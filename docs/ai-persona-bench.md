# AI 페르소나 투표 — 로컬 LLM 벤치마크

AI 페르소나 기능(질문자가 조건과 명수를 정하면, 조건에 맞는 가상 인물들이 선택지 하나와 한 줄 이유로 답한다)을 만들기 전에,
로컬 GPU 에서 LLM 이 얼마나 빨리, 얼마나 쓸 만하게 답하는지 실측했다. 실험 코드는 `spikes/llm-bench/` 에 있다.

실험일: 2026-09-30

## 1. 환경

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 5070 Ti 16GB (16,303 MiB), 드라이버 616.92 |
| 실험 중 다른 프로그램의 VRAM 사용 | 약 2.0GB (Chrome, IntelliJ, Docker Desktop 등. 안드로이드 에뮬레이터는 종료) |
| Ollama | 0.34.2 (Windows 트레이 앱) |
| Ollama 설정 | `OLLAMA_NUM_PARALLEL=8`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`. 기본값은 `NUM_PARALLEL=1`, flash attention 꺼짐, KV 캐시 f16 |
| 모델 | `exaone3.5:7.8b` (LG AI Research, Q4_K_M, 4.8GB), `qwen3:14b` (Q4_K_M, 9.3GB, `think: false`) |
| 요청 | Ollama `/api/chat`, structured output(JSON 스키마, `choice` 는 선택지 enum), `num_ctx 4096`, `temperature 0.8`, 시드 없음 |
| 클라이언트 | Python 3.13 표준 라이브러리, 스레드로 동시 요청 |

모델 후보를 이렇게 고른 이유: 16GB 에서 KV 캐시까지 올리려면 14B Q4 가 상한이다. exaone 은 한국어 학습 비중이 높은 국내 모델이고, qwen3:14b 는 같은 VRAM 에 들어가는 범용 모델 중 한국어가 되는 대표 모델이다. Qwen3 의 "생각" 모드는 답 앞에 수백 토큰이 붙어 껐다.

## 2. 실험 재료

- **페르소나 100명**: `spikes/llm-bench/personas.py` 가 고정 시드(20260930) 난수로 만든다. 연령대(20~30대 68%), 성별(반반), 연애 상태(솔로/썸/연애 중/기혼), 직업군 12종, 한 줄 성격(기질 + 태도), 관심사 2개. 연령대에 어울리는 직업·연애 상태만 고른다.
- **질문 3개** (`scripts/local/sample-data.sql` 의 글형 고민):

  | id | 고민 | 선택지 | 보려는 것 |
  |---|---|---|---|
  | date | 소개팅 첫 만남, 어디가 좋을까요? | 카페 / 밥집 | 연애 상태·연령대와 답의 연결 |
  | job | 이직 제안을 받았어요. 연봉은 10% 오르는데 출퇴근이 40분 늘어납니다. | 이직한다 / 남는다 | 성격(안정 지향 / 도전 지향)과 답의 연결 |
  | hobby | 새 취미를 시작하려고 합니다. 하나만 골라 주세요. | 기타 / 수영 / 베이킹 / 보드게임 | 관심사(음악→기타, 운동→수영, 요리→베이킹, 게임→보드게임)와 답의 연결 |

- **출력 형식**: `{"answers":[{"personaId":1,"choice":"카페","reason":"…"}]}`. 이유는 40자 이내.
- **프롬프트**: system 에 역할과 형식 규칙, user 에 고민·선택지·인물 목록(한 줄씩). 묶음 방식은 인물 N명을 한 요청에 넣는다.

## 3. 비교한 방식

| 방식 | 뜻 | 요청 수 |
|---|---|---|
| A `1x1` | 1명씩, 차례대로 | 100 |
| B `25x1` | 25명 묶음, 차례대로 | 4 |
| C `1x8` | 1명씩, 동시에 8개 | 100 |
| D `5x4` | 5명 묶음, 동시에 4개 | 20 |

(결과를 보고 추가한 방식은 4장에 따로 적었다)

## 4. 측정 방법

- 시간: 요청을 보내기 시작해서 마지막 응답까지의 벽시계 시간. 모델 로딩은 예열 호출로 뺐다.
- 생성 tok/s (전체) = 생성 토큰 합 ÷ 벽시계 시간 (처리량). tok/s (요청당) = Ollama 의 `eval_count ÷ eval_duration` (요청 하나가 보는 속도).
- 첫 결과: 첫 응답(1명 또는 첫 묶음)이 도착한 시각.
- 형식 실패: 재시도 없이 센다. 요청 오류, JSON 파싱 실패, personaId 누락·중복, 선택지 밖의 choice, 빈 이유, 40자 초과.
- 다양성: 선택지 분포, 이유의 정확 중복률, 이유 사이 평균 유사도(글자 2-gram 자카드, 0 이면 완전히 다름), 속성-답 연결 지표.
- VRAM: `nvidia-smi` 1초 폴링 최대값.

### 5.1 읽는 법

- **동시 처리가 핵심이다.** exaone 은 1명씩 차례로(1x1) 33초가 걸리지만, 같은 요청을 8개씩 동시에 보내면(1x8) 11~13초, 5명 묶음을 4개 동시에(5x4) 9~11초다. 처리량(전체 tok/s)이 120 → 320~370 으로 3배 가까이 오른다. 요청 하나가 보는 속도는 절반 이하로 떨어지지만(144 → 50~90 tok/s) GPU 가 쉬는 시간이 없어진다.
- **동시 4개면 이미 포화다.** 5x4 와 5x8 의 전체 시간이 같다(exaone 9.9 vs 8.9초, qwen3 19.6 vs 17.6초). 이 GPU 에서 7.8B 모델은 동시 4개로 거의 다 채운다.
- **큰 묶음은 첫 결과가 늦다.** 25x4 는 전체 시간은 가장 짧은 축이지만(9~11초) 첫 결과가 8초 뒤에 온다. 5x4 는 1.5~2초, 1x8 은 0.7초에 첫 답이 온다. 화면에 답을 하나씩 채워 보여 주려면 작은 묶음이 낫다.
- **qwen3:14b 는 모든 방식에서 exaone 의 약 2배 시간**이다(5x4 기준 20~28초). VRAM 도 15.5~15.7GB 까지 차서(전체 16.3GB) 다른 프로그램이 조금만 더 쓰면 CPU 로 밀릴 여지가 있다. date 1x8 에서 첫 결과가 14.5초나 걸린 실행은 이런 경계 상황으로 보인다(job 1x8 은 2.1초).
- **형식 실패는 전부 "이유 40자 초과"** 였다. JSON 파싱 실패, 선택지 밖의 값, personaId 누락은 0건이다(스키마로 강제한 결과). 40자 초과는 1명씩 물을 때 잦고(exaone 1x1/1x8: 2~9%), 묶음에서는 거의 없다(0~1%). 실제 기능에서는 40자에서 잘라 쓰거나 그 건만 다시 물으면 된다.
- **편차**: 같은 조건을 다시 돌리면 5x4 는 ±1초, 1x8 은 ±2초 안에 들어왔다. 다만 exaone hobby 1x8 의 첫 실행(23.2초)과 5x4 첫 실행(15.2초)은 재실행(12.7초, 11.1초)에서 재현되지 않았다. 요청별 기록을 보면 그 시간대에 요청당 속도가 절반으로 떨어져 있었다(54 → 27 tok/s). GPU 를 다른 프로그램이 쓰고 있었던 것으로 추정하며, 실험은 사용 중인 PC 에서 돌렸으므로 이런 흔들림을 감안해야 한다.

### 6.1 읽는 법

- **1명씩 물으면 페르소나가 가장 잘 반영된다.** 관심사와 맞는 취미를 고른 비율이 1x1/1x8 에서 exaone 67~81%, qwen3 94~96% 인데, 25명 묶음에서는 41~65% 로 떨어진다. 5명 묶음은 그 사이(exaone 41%, qwen3 57%), 10명 묶음은 exaone 51%, qwen3 76%. 인물이 많이 들어갈수록 모델이 한 명 한 명의 속성을 덜 본다.
- **"안정 지향" 성격은 어느 방식에서든 잘 반영됐다.** 이직 질문에서 안정 지향 성격 21명이 "남는다"를 고른 비율이 모든 조건에서 71~100% 다. 성격 문구가 질문과 직접 맞닿아 있으면 묶음에서도 살아남는다.
- **연애 상태와 소개팅 장소는 약하게만 연결된다.** 솔로가 카페를 고르는 비율이 기혼보다 대체로 높지만(exaone 5x4: 솔로 61% vs 기혼 26~32%) 방식마다 흔들린다. 어느 쪽이 "맞는" 답인지도 없으므로 참고만.
- **큰 묶음에서 qwen3:14b 는 이유를 복사한다.** 25명 묶음의 이유 정확 중복이 17~40% 다 (job 25x1 에서 "시간이 더 중요해 보여서 이직은 안 할 거다" 가 11번). exaone 은 어느 조건에서도 5% 이하다. 앱에서 같은 문장이 여러 명에게 붙어 있으면 바로 티가 나므로 qwen3 을 쓴다면 큰 묶음은 피해야 한다.
- **묶음은 선택지 분포를 고르게 만든다.** qwen3 은 1명씩 물으면 카페 74~79% 로 쏠리는데 5명 묶음이면 57~59% 다. exaone 은 어느 방식에서든 반반이다. 묶음에서는 모델이 인물들 사이에 답을 나눠 주는 경향이 있다. 다양해 보이지만 개별 인물의 속성에서 나온 다양성은 아닐 수 있다(위 관심사 일치율 하락과 같은 현상).
- 이유 문장 사이 평균 유사도(2-gram 자카드)는 모든 조건에서 0.03~0.15 로 낮다. 1x1 이 가장 높은 편인데(0.145) 같은 인물이 아니라 같은 표현("편안한 분위기에서 대화")이 반복돼서다.

- 두 모델 모두 40자 안에서 "그 사람 상황이 드러나는 한 줄" 은 쓴다. 기혼 30대가 소개팅 질문에 답하는 어색함은 페르소나 데이터 쪽 문제이고, 실제 기능에서는 질문자가 고른 조건으로 걸러지므로 생기지 않는다.

## 8. 추천 설정

| 항목 | 추천 | 이유 |
|---|---|---|
| 모델 | **`exaone3.5:7.8b`** | qwen3:14b 의 절반 시간, 형식 실패율 같거나 낮음, 이유 복사 없음, 선택지가 쏠리지 않음. VRAM 7GB 로 여유가 4GB 이상 남는다. qwen3:14b 는 1명씩 물을 때 속성 반영이 더 좋지만(96%) 2배 느리고 VRAM 이 꽉 찬다 |
| 묶음 크기 | **5명** | 1명은 속성 반영이 가장 좋지만 40자 초과가 잦고 요청 수가 인원만큼 늘어난다. 25명은 첫 결과가 6~8초 늦고 속성 반영이 떨어진다. 5명은 형식 실패 1/500(5회 실행 합계, 40자 초과 1건), 첫 결과 1.5~2초 |
| 동시 요청 | **4개** (`OLLAMA_NUM_PARALLEL=4`) | 8개로 늘려도 전체 시간이 같다. 4개면 KV 캐시가 절반이라 VRAM 여유도 커진다 |
| 예상 시간 (exaone, 5x4) | 100명 9~11초, 20명이면 요청 1묶음 ≈ 2초 | 실제 기능은 한 질문에 수십 명이므로 2~5초 안에 끝난다 |
| 기타 | flash attention 켜기, KV 캐시 q8_0, `think: false`, 출력은 JSON 스키마(choice enum, answers 개수 고정)로 강제 | 5장 실패 종류 참고. 40자 초과는 잘라서 쓴다 |

속성 반영이 더 중요해지면(예: "연애 중인 사람들만 골라서 물었는데 답이 다 비슷하다"는 피드백) 묶음을 1명으로 줄이고 동시 8개로 보내는 것이 다음 선택지다. 시간은 +20~30%, 40자 초과 재요청이 5% 안팎 생긴다.

## 9. 실험하면서 알게 된 것

- **형식 예시의 번호를 베낀다.** 프롬프트 예시에 `"personaId":1` 을 넣었더니 1명씩 물을 때 인물 #2, #3 에게 물어도 답은 personaId 1 로 왔다(exaone 1x1 에서 99/100 이 불일치). 예시에는 실제 인물 번호를 넣어야 한다.
- **묶음에서 중간에 멈춘다.** 25명을 물었는데 exaone 이 1명, 6명만 답하고 끝낸 경우가 있었다(첫 시도에서 43/100 누락). JSON 스키마에 `answers` 의 `minItems`/`maxItems` 를 인원수로 넣어 문법 수준에서 막았고, 그 뒤로 누락은 0건이다. 이것은 실제 기능에서도 그대로 써야 한다.
- **JSON 을 한 줄로 쓰게 해야 한다.** 그러지 않으면 들여쓰기 공백에 토큰의 1/3 을 쓴다.
- **Qwen3 의 생각 모드는 꺼야 한다.** `think: false` 없이는 답 앞에 수백 토큰이 붙는다.
- **PC 를 쓰면서 재면 흔들린다.** 5.1 의 편차 항목 참고. 서비스에서는 전용 GPU 가 아니라면 이 정도 흔들림을 전제해야 한다.
- 계획한 51회 중 46회를 돌렸다. qwen3:14b 의 hobby 5x8 과 반복 실행 4개는 시스템 RAM 부족으로 실행이 중단되어 돌리지 못했다. qwen3 은 추천 모델이 아니라 결론에는 영향이 없다.

## 10. 다시 돌리려면

cd spikes/llm-bench
